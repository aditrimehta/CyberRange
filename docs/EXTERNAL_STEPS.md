# External steps for operators

1. **Prepare the host.** Use a dedicated supported Linux server or VM. Install Docker Engine 27 or later and the Docker Compose v2 plugin 2.30 or later. These versions are the deployment baseline selected for this project; verify the versions with `docker version` and `docker compose version`. A practical starting host is 8 vCPU, 32 GiB RAM, and 200 GiB free SSD for a small class. Budget approximately 2.5–3 GiB RAM, 1–1.5 CPU cores, and 0.5–1 GiB writable disk per concurrent session, plus 6–10 GiB for the attacker image, 1–2 GiB for the legacy Metasploitable target, platform services, image layers, and backups. Capacity is `min((RAM_GiB - platform_reserve_GiB) / session_RAM_GiB, (CPU_cores - platform_reserve_cores) / session_cores, free_session_disk_GiB / session_disk_GiB)`, rounded down. Start with a reserve of 6 GiB and 2 cores for the platform; measure actual labs before raising concurrency.

2. **Build and pull images.** From the repo root run `make build-images`. The custom attacker desktop is the largest image; plan for about 5–8 GiB for the Kali image and 0.2–1.5 GiB for each target, with 30–90 minutes for the first uncached build on a normal broadband host. These are planning estimates, not measured outputs. Third-party images in use are `postgres:16.6-alpine`, `tecnativa/docker-socket-proxy:0.3.0`, `traefik:v3.2.2`, `axllent/mailpit:v1.22.3`, `kalilinux/kali-rolling:latest`, `python:3.12.8-slim-bookworm`, `debian:bookworm-slim`, `alpine:3.21.0`, `tleemcjr/metasploitable2:latest`, `node:22.12.0-alpine`, and `nginx:1.27.3-alpine`. Verify pulls with `docker pull IMAGE:TAG` for each image; `make build-images` performs the custom builds and explicitly pulls Metasploitable2. If a tag has moved or disappeared, review the upstream image's release notes, select a maintained version, pin its digest in the Dockerfile or manifest, rebuild, and rerun the smoke test. Docker Hub can rate-limit anonymous pulls; authenticate with `docker login` using an institution-approved account or configure a pull-through cache. Recheck all upstream images before a production term because tags and vulnerabilities change.

3. **Domain, DNS, and TLS.** Set `DOMAIN` to the institution-controlled hostname and `ACME_EMAIL` in `.env`. For Let's Encrypt HTTP-01, create a public A/AAAA record pointing to the server and allow inbound TCP 80 and 443. Start with `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`. For a campus-only network, use a certificate issued by the institution's internal CA and distribute its trust root to managed student browsers, or use a self-signed certificate only for a controlled pilot. Configure the proxy certificate and keep `SECURE_COOKIES=true` whenever HTTPS is active.

4. **Email.** Obtain an approved SMTP relay and credentials. Set `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, and `SMTP_PASSWORD` in `.env`; use the relay's required TLS port and verify delivery before enabling `REQUIRE_EMAIL_VERIFICATION=true`. Teacher onboarding and password-reset messages use these settings. In development, `make dev` starts Mailpit and publishes its inbox only on `127.0.0.1:8025`; do not enable the Mailpit profile in production.

5. **Secrets.** From a secure shell run `openssl rand -hex 32` for `POSTGRES_PASSWORD` and `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'` for `SESSION_SECRET`. Put both values in `.env`, set `APP_ENV=production`, `SECURE_COOKIES=true`, and `RUNTIME=docker`. Do not commit `.env`. Restrict it with `chmod 600 .env`. Use a secrets manager for production deployments. Set `REQUIRE_EMAIL_VERIFICATION=true` only after confirming SMTP delivery.

6. **First run.** Run `make build-images`, then `RUNTIME=docker docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`. Migrations run during API startup; lab sync also runs at startup. Confirm with `docker compose exec api python -m app.cli labs validate` and `docker compose exec api python -m app.cli labs sync`. Create the first administrator with `docker compose exec api python -m app.cli create-admin`, sign in, change any temporary password, and accept the AUP. Do not run `make seed` in production.

7. **Network and firewall.** Permit inbound TCP 80/443 only. Do not publish 5432, 2375, 6080, 5901, or target ports. Verify the listening sockets with `sudo ss -lntp` and the compose bindings with `docker compose ps`. Confirm PostgreSQL and `socket-proxy` have no host port mappings: `docker inspect "$(docker compose ps -q db)" --format '{{json .NetworkSettings.Ports}}'` and `docker inspect "$(docker compose ps -q socket-proxy)" --format '{{json .NetworkSettings.Ports}}'`. At the host firewall, allow only the institution-approved sources and service ports.

8. **Smoke test.** Ensure demo data exists only in a non-production smoke environment. Set `RUNTIME=docker` for the shell, start the stack, then run `RUNTIME=docker make smoke` or `RUNTIME=docker bash scripts/smoke_test.sh`. The script checks lab validation, API health, all six lab launches, the desktop route, attacker-to-target reachability, no target host ports, lack of internet egress, and cleanup. `PASS` means that check completed on this host; `FAIL` identifies the first failed condition. It requires `curl`, `jq`, Python 3, Docker CLI, and the seeded demo student. Run it again after updating images, proxy labels, or Docker.

9. **Institutional and legal approval.** Obtain written approval from the institution's IT/security office before exposing the service or vulnerable images. Publish and require acceptance of an acceptable-use policy. Tell students that activity is logged. Use a dedicated host or isolated VM because Docker shares the kernel with the host and the API has Docker control-plane authority.

10. **Backups and updates.** Schedule `BACKUP_DIR=/secure/backups bash deploy/backup.sh` with the host scheduler (for example, a daily systemd timer). The script produces a PostgreSQL custom-format dump; encrypt and copy it off-host. Restore into an empty target database with `docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' < backup.dump`. To update, take and verify a backup, review image/dependency changes, run `make build-images`, deploy with `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`, and confirm migrations, health checks, and smoke tests.

11. **Checks not run in the build sandbox.** This workspace had no Python interpreter and no Docker Engine, so install the host requirements above, then run `python3 -m venv .venv && . .venv/bin/activate && pip install -e 'backend[dev]' && (cd backend && pytest --cov=app --cov-report=term-missing)`. Verify the frontend with `cd frontend && npm install && npm test && npm run lint && npm run build`. On a prepared fake-mode Compose host, run `make seed && make e2e`. On the isolated Docker host, run `make build-images && RUNTIME=docker make dev-docker`, then `RUNTIME=docker make smoke`. These commands are the verification steps for package installs, full migrations, Playwright flow, image build, no-egress behavior, reverse-proxy desktop routing, and reaper cleanup.
